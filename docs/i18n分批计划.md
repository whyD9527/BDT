> **口径补充 3（E7 批次踩到两个编译坑 + 一个 CI 判读坑，都很值钱）**：
> 1. **`stringResource` 只能出现在 @Composable 上下文**：`onLongClick = { … }` 这种**非 composable 回调**里
>    编译报 `@Composable invocations can only happen from the context of a @Composable function`
>    （CI 在 `compileAlphaReleaseKotlin` 报）；这种地方要用 `context.getString(R.string.x)`；
> 2. **新文件必须自己 import**：`VideoCodingInfoScreen.kt` 里我用了 `stringResource`/`R` 但**没 import**
>    → CI 报一屏 `Unresolved reference 'stringResource' / 'R'`。**已把这条加进本地校验脚本**
>    （`tools`/`/tmp/validate_bdt.py`：扫所有 kt，`stringResource(` 必须有对应 import；根包 `com.imcys.bilibilias`
>    里 `R` 同包、不需要 import）；
> 3. **怎么判断 release 打包真的失败了**（`continue-on-error` 会掩盖）：REST API 里
>    `Assemble alphaRelease` 的 `conclusion` 永远是 `success`，**真正的信号是 `Fallback to alphaDebug` 是
>    `skipped` 还是 `failure`** —— 它非 skipped 就说明 release 那步的 outcome 是 failure（本轮两次红都是这么看出来的）；
> 4. **数据值不抽的实例**：`ep.badge != "会员"`（与接口返回的字符串比对，抽了会让"非会员剧集"过滤失效）、
>    `keywordColorMap` 的键（高亮匹配用）、线路名/命名规则 token；
> 5. 扫描器已修：多行调用的字面量现在会**回溯 6 行**归类（此前 `trace(` 换行写的会被误算成 `ui`），
>    修正后 `ui` 由粗算 345 → **299**（真实待抽比这还少，因为含上面的数据值）。

> **口径补充 2（E6a/E6b 发现）**：
> 4. **替换要"注释感知"**：`SettingScreen` 里还留着注释掉的旧代码，里面有**同样的字面量**
>    （`// text = "命名规则",`）—— 直接 `str.replace` 会命中 2 次而断言失败（我这次就撞上了）。
>    正确做法：只替换**不在 `//` 之后**的那一处（脚本里已实现 `replace_active`）；
> 5. **文件名/数据值一律不动**：设置备份文件名 `BDT-设置备份-<ts>.json`（改成随语言变的名字反而更糟）；
> 6. **默认参数里的文案**也要改：`StorageContent(buttonText: String = "管理")` 这种默认值拿不到
>    Composable 上下文 → 改成 `@StringRes buttonTextRes: Int = R.string.storage_manage`。

> **口径补充（E5 发现，看数字时记得扣掉）**：
> 1. **`@Preview` 的参数默认值不算 UI 文案**：`WorkCard` 里剩下的 5 处（`title = "标题"`、`upName = "UP主"`）
>    只在 IDE 预览里出现，而且默认参数拿不到 Composable 上下文 → 按计划**不动**，但扫描器会算进 `ui` 桶；
> 2. **枚举里的文案要存 `@StringRes`**：`ToolInfo` 的 enum 项写死中文（enum 里没有 Context），
>    本批改成 `@StringRes val titleRes/descRes`；⚠️ 它是**持久化用的枚举**（存的是 `name`），

>    已改成 `key(tool.name)`（稳定）。

> ⚠️ **教训（本批踩到）**：alpha workflow 开了 `cancel-in-progress: true` —— 上一批还没跑完就推下一批，
> **会把上一次 run 直接取消**，那一批就没有独立的验证记录（E2 就是这样，靠 E3 的 run 顺带覆盖了它的树）。
> 规矩：**一批一推，等 CI 双绿再推下一批。**

## 结论

- 实测规模：**72 个文件 / 686 处**硬编码中文；`ui=600 internal=20 diag=66`；
- **`ui` 是上界**：分类是**行级**启发式，多行拼接的诊断文案（字面量与 `trace(` / `Log.*` 不在同一行）
  会落进 `ui` 桶（如 `FileOutputManager` 的交付日志）。真正要抽的比 600 少。
- **不翻译的三类**（扫到也**不要**动）：
  1. `diag`：日志与轨迹（`Log.*` / `trace(` / `logDiagnostic(`）—— 这是给排查用的，中英混排反而更难搜；
  2. `internal`：异常/断言消息（`IllegalStateException("…")`）—— 开发者看的；
  3. **数据值**：如 `BILILineHostItem("默认线路", …)`、画质/编码的展示名 —— 它们是"平台数据"，
     抽成资源会让"数据"和"界面"混在一起（这类要单独评估，别硬抽）。

## 分批原则

1. **一批 = 一个界面/一个功能簇（1–3 个文件）**，不要跨界面批量替换（交接文档 §八 第 3 条：
   全局替换曾把 `BILIBILIASTopAppBarStyle` 改坏）；
2. 每批的动作固定为：抽 `values/strings.xml` + `values-en/strings.xml` → 改调用点（`stringResource`/`getString`）
   → 跑本地校验（XML 可解析、无裸 `<`/撇号、`R.string` 引用都在）→ 推 main → 看 CI 双绿；
3. **优先级**（按用户实际会看到的面来排）：
   1. 下载相关：`DownloadScreen` / `DownloadTaskCard` / `DownloadViewModel` / `DownloadFinishTaskCard`
   2. 首页与工具：`HomeScreen` / `ToolsScreen` / `WorkCard`
   3. 设置与存储：`SettingScreen` / `StorageManagementScreen` / `SettingViewModel`
   4. 解析：`AnalysisScreen` / `AnalysisViewModel` / `VideoCodingInfoScreen`
   5. 其它（登录、用户页、番剧、投诉、版本页…）
4. **键名规范**：沿用现有风格 `<界面>_<用途>`（如 `download_batch_delete_title`），避免与被扫描出的
   中文做"一词一键"的机械对应；
5. **英文翻译**要"像人话"，不要直译工具腔（现有 `values-en` 已经是这种风格）。
