## 结论

- 实测规模：**72 个文件 / 686 处**硬编码中文；`ui=600 internal=20 diag=66`；
- **`ui` 是上界**：分类是**行级**启发式，多行拼接的诊断文案（字面量与 `trace(` / `Log.*` 不在同一行）
  会落进 `ui` 桶（如 `FileOutputManager` 的交付日志）。真正要抽的比 600 少。
- **不翻译的三类**（扫到也**不要**动）：
  1. `diag`：日志与轨迹（`Log.*` / `trace(` / `logDiagnostic(`）—— 这是给排查用的，中英混排反而更难搜；
  2. `internal`：异常/断言消息（`IllegalStateException("…")`）—— 开发者看的；
  3. **数据值**：如 `BILILineHostItem("默认线路", …)`、画质/编码的展示名 —— 它们是"平台数据"，
     抽成资源会让"数据"和"界面"混在一起（这类要单独评估，别硬抽）。

## 分批原则

1. **一批 = 一个界面/一个功能簇（1–3 个文件）**，不要跨界面批量替换（交接文档 §八 第 3 条：
   全局替换曾把 `BILIBILIASTopAppBarStyle` 改坏）；
2. 每批的动作固定为：抽 `values/strings.xml` + `values-en/strings.xml` → 改调用点（`stringResource`/`getString`）
   → 跑本地校验（XML 可解析、无裸 `<`/撇号、`R.string` 引用都在）→ 推 main → 看 CI 双绿；
3. **优先级**（按用户实际会看到的面来排）：
   1. 下载相关：`DownloadScreen` / `DownloadTaskCard` / `DownloadViewModel` / `DownloadFinishTaskCard`
   2. 首页与工具：`HomeScreen` / `ToolsScreen` / `WorkCard`
   3. 设置与存储：`SettingScreen` / `StorageManagementScreen` / `SettingViewModel`
   4. 解析：`AnalysisScreen` / `AnalysisViewModel` / `VideoCodingInfoScreen`
   5. 其它（登录、用户页、番剧、投诉、版本页…）
4. **键名规范**：沿用现有风格 `<界面>_<用途>`（如 `download_batch_delete_title`），避免与被扫描出的
   中文做"一词一键"的机械对应；
5. **英文翻译**要"像人话"，不要直译工具腔（现有 `values-en` 已经是这种风格）。
