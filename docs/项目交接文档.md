### 第七轮：切断「已不在原作者控制下」的域名（2026-09-12，安全问题）

**发现**：App 仍在使用 `api.misakamoe.com`（原作者的服务器）做**更新检查与公告**，
而这个域名**已经不在原作者手里**了。用 Cloudflare DoH 查真实解析（绕开本机 fake-IP 代理）：

```
api.misakamoe.com → cf.468123.xyz → saas301.pages.dev → Cloudflare（172.66.47.45 / 172.66.44.211）
```

免费域名服务 + 他人 Cloudflare Pages 站点，直连返回 200 空响应。

**为什么危险（每一环都有证据）**：
1. `HomeViewModel.initOldAppInfo()` 请求 `bilibilias.php?type=json`，取回 `version / notice / url`；
   同域名的 SSE `/bilibilias/events/subscribe` 还能推 `appUpdate` 事件
   （注：SSE 订阅此前已被注释掉，**HTTP 那条是活的**）；
2. 数据直接变成首页弹窗：`HomeScreen` 里「远程版本 ≠ 本机版本就弹窗」，
   且构造时写死 `forcedUpdate = true`，点确认即 `openLink(appUpdateInfo.url)` —— **URL 完全由远程决定**；
3. 响应里的 `apkmD5` 字段**全仓库没有任何校验逻辑**（只存在于数据类声明中）。

> **净效果**：谁控制那个域名，谁就能让所有已安装用户看到一条"立即更新"弹窗，
> 并把他们导向任意下载地址。这不是"代码不够整洁"，而是一条可被远程利用的投递路径。

**处理（纯删除，已本地编译验证）**：
- 删除 `AppAPIService`（8 个方法）＋ 6 个 `AppOld*Bean` ＋ `API.App` 里全部 `OLD_*` / `SSE_*` 常量；
- `HomeViewModel` 移除更新检查 / 公告 / banner 拉取与整段 SSE 代码，`HomeScreen` 去掉调用；
- 顺手清掉另外三条同样依赖该服务器的**死功能**：
  - **充电专属 BoostVideo**：数据取不到时 `boostVideoInfo?.code != 0` 恒为真，
    导致这类视频的下载区**永远不渲染**（现存 bug）；删除后改由 B 站自身的 `isUpowerPlay` 判断；
  - **视频冻结（SoFreeze）**：3 个对话框 + ViewModel 方法，其触发按钮此前已被注释掉，不可达；
  - **漫游申请 / 捐赠**：服务已死；捐赠路由此前已无入口。
- 「漫游服务」设置项一并移除（它的开关 `roamEnabled` **只写不读**，从来没有真正生效过）。

> 保留下来的东西：`KtorDI` / `RoamPlugin` / `QRCodeImage` 中**提到 misakamoe 的注释**予以保留，
> 它们记录了"为什么不能用"，是有价值的历史说明。

> 待办：更新提示若要恢复，应改读本仓库自己的 GitHub Releases（`api.github.com` 本机可达），

### 第八轮：接口规则集中化（Step 2，2026-09-12，纯内部重构）

**为什么做**：同一条请求头规则原先**散在三处、而且互相矛盾** ——

| 位置 | 它对「TV 平台要不要 UA / Referer」的答案 |
|---|---|
| `AutoBILIInfoPlugin`（Ktor 业务请求） | 对 4 个 TV 端点**删掉** UA 和 Referer |
| `KtorDI` 的 OkHttp 拦截器（下载） | 只补 Referer，不补 UA |
| `LineConfigViewModel.speedTest`（裸 `java.net`） | TV 用 `"Mozilla/5.0"`，Referer 是个具体视频页 |

2026-09 那次「下载必然 403」就是这类不一致造成的：CDN 请求被按 TV 规则删了头。
规则不改的话，同类 bug 换个形式还会复发。

**做法（行为完全不变，只搬位置）**：
- 新增 `core/network/config/RequestRules.kt` —— **请求头与媒体主机的唯一真相源**：
  媒体 CDN 关键字、TV 端点"去头"名单、默认 Referer/UA、测速用的 UA/Referer、
  以及原硬编码在 `DownloadExecutor.replaceCdn()` 里的 UPOS 主机正则；
- 新增 `core/datastore/ParsePlatformExt.kt` —— 平台判定 `isTv` / `isWeb` / `isMobile`：
  原先「是不是 TV」在 6 处各写一遍且分组写法不一致（`Web, Mobile, UNRECOGNIZED ->`
  与 `Mobile, UNRECOGNIZED, Web ->` 其实是同一件事）；
- 上述三处请求头逻辑、`RoamPlugin`、`VideoInfoRepository` 两处 `when`、
  `DownloadExecutor` 全部改为引用这两个真相源。

**刻意保留的矛盾**（写在 `RequestRules` 注释里，别顺手"统一"）：
测速的 Referer 与默认 Referer 不同、TV 端点的"去头"规则与 CDN 的"补头"规则方向相反 ——
都是既有行为，改了需要真实证据。

> ⚠️ **一个需要证据才能改的点**：CDN 关键字里的 `"edge"` 过于宽泛。
> 想收窄成显式域名（`edgekey.net` 等）**必须先抓真实下载的 logcat** 看命中了哪些 host，
> 凭猜改会漏掉真 CDN → 重现 403。方法写在 `RequestRules` 的注释里。

> 验证：本地 `:app:compileAlphaDebugKotlin` 通过；逐行核对 diff 确认分支顺序与取值未变；
> 全仓库已无散落的 `VideoParsePlatform.TV` 比较与硬编码请求头字面量。

### 第九轮：签名与状态加固（Step 3，2026-09-12）

**修的四个确定性缺陷**（签名结果逐字节不变）：

1. **wbi key 永不刷新** —— `WebiTokenUtils` 只在 `key == null` 时取一次，
   B 站一旦轮换 wbi key，所有 wbi 接口会一直失败**到 App 重启**为止。
   现在按 TTL 刷新（有 key 时 6 小时、无 key 时 30 秒重试），`@Volatile` + `Mutex` 去重，
   且**刷新失败保留旧 key**（原写法会把 key 清成 null，导致后续签名直接抛异常）。
2. **越界崩溃（off-by-one）** —— mixKey 长度判定原为 `>= 置换表最大值(63)`，
   而长度恰为 63 时 `mixKey[63]` 会 `IndexOutOfBoundsException`；正确要求是 **> 63**。
3. **`BiliAppSigner.appSign` 修改调用方的 map** —— 原先往里 `put("appkey")`，
   调用方复用该 map 就会莫名多出一个参数；现在只在内部副本上改。
4. **`RiskControlPlugin` 读每个响应的 body** —— 原先不分请求类型把响应体整份读成字符串，
   实际只有 3 个播放接口需要检查风控字段；现在**先判 URL 再读 body**。判定结果不变。

**顺手收拢**：MD5 实现原先两份（App 签名 / wbi 签名各一），合并为 `Md5.kt`。
已用 JVM 实测证明两者等价 —— 全部 256 个字节值下
`String.format("%02x", byte)` 与掩码写法输出完全一致（0 处不同），
所以这次合并**不会改变任何签名值**。

**刻意保留的耦合**（注释里已说明理由）：`encWbi` / `checkToken` 仍是
`BILIBILIWebAPIService` 的扩展函数 —— 因为刷新 key 必须调用该 service 的接口
（`getWebIInfoNoCheckLogin`）；为解耦而改 7 个调用点收益不抵风险。

> 验证：本地编译通过；JVM 实测 md5 等价；逐行核对 diff（**这一步抓到过一次
> 意外改动**：重写 `BiliAppSigner` 时我误删了随机字符集里的一个 `l`，
> 会导致设备指纹字符分布变化 —— 已改回并复核 diff 中不再出现该行）。

### 第十一轮：3.1.7 回归事故与 3.1.8 热修（2026-09-12）

**症状**：装上 3.1.7 后，用户页出现两处报错：
`Illegal input: Fields [birthday, coins, face, …, mid, name, rank, sex, …] are required`，
且关注/粉丝/获赞/播放全为 0。

**根因（第九轮我自己引入的回归）**：重写 `WebiTokenUtils.setKey()` 时**丢了 `.take(32)`**。
官方 wbi 算法的置换表有 64 项，但**只取前 32 项**组成 mixin key；丢掉 take 后 key 变成 64 字符，
**所有 wbi 签名全部失效** —— 而用户页的 `x/space/wbi/acc/info` 与 `x/space/wbi/arc/search`
正好都是 wbi 接口。

**为什么报错长成那样**：B 站对签名异常按风控处理，返回
```json
{"code": -352, "message": "风控校验失败", "ttl": 1, "data": {"v_voucher": "voucher_..."}}
```
而 `BiliApiResponseSerializer` 只判断"有 data 就当成功结构解析"，
于是拿 `{"v_voucher": ...}` 去解 `BILIUserSpaceAccInfo`；模型字段**全无默认值** →

### 第十四轮：多线程分片下载 —— 摸底与方案（**待实施**）

**现状（摸底结果，只读调查）**

调用链：
```
DownloadScreen → NewDownloadManager.addDownloadTask()
  → 队列服务 startDownloadQueue → executeTaskDownload → downloadAppTask
     → 子任务 ≥2：downloadMultipleSubTasks（音/视频各一个 async，**已并发**）
       子任务 =1：downloadSingleSubTask
     → downloadSubTask → VideoInfoFetcher 解析出 URL
     → DownloadExecutor.downloadFile(url, savePath, referer, onProgress)
     → 成功后 handleSuccessor → FfmpegMerger.mergeMedia → updateTaskAndCleanup
```

`DownloadExecutor`（190 行，**单文件单连接**）：
- `HEAD` 取 Content-Length；目标文件已存在且不小于远端长度 → 直接判定完成
- 失败重试 **5 次**，每次重试都复用同一个 URL（URL 过期会导致 5 次全失败）
- `Range: bytes=<已下载>-` 断点续传，64KB buffer 顺序写，进度按 `Content-Length + 已下载` 计算
- 进度回调按 1% 节流；**显式检查 HTTP 状态码**（403/404 不再被当成正文写入）
- `replaceCdn()` 按设置把 `upos-sz-estg*.bilivideo.com` 换成用户选的线路

**有利条件（说明改造可行）**：① 已在用 `Range` → CDN 支持 206；② 音/视频两路并发已在跑
→ 并发模式有先例；③ 进度聚合已有"两路取平均"的先例；④ `activeDownloadJobs` 按 segment
取消，分片协程若挂在同一父 Job 下即可被一起取消。

**要小心的点**：① 状态机与 Room（`DownloadSegment.downloadState`、`updateSegment`）不改语义；
② **不动 DB 表结构**（加分片元数据要走边车文件，避免 Room 迁移）；③ 不要碰
`FfmpegMerger` / 命名约定 / 字幕 / 封面 / 前台服务；④ 并发可能触发 CDN 风控（要限并发数 + 可降级）；
⑤ 分片写入的偏移必须精确（现有实现只比长度、不校验内容）；⑥ 暂停/取消要能把所有片停住。

**方案（待确认后实施）**

把一个文件的下载改成 **N 片并发**，且**只改 `DownloadExecutor` 内部** ——
上层调用链、状态机、DB、Merger **完全不动**，进度语义保持不变。

| 设计点 | 选择 |
|---|---|
| 触发条件 | `Content-Length ≥ 8MB` 且 HEAD 支持 `Accept-Ranges: bytes`；否则**回落现有单连接** |
| 分片 | 固定片大小（如 4MB）或按并发数均分，尾片单独处理 |
| 并发度 | 默认 4（可设置），避免触发风控 |
| 落盘 | **预分配单文件** + 每片 `RandomAccessFile` 定位写入；每片进度记在**边车文件**（`.downloadpart`），不动 DB |
| 断点续传 | 按边车元数据核对每片已完成长度，只重下未完成/长度不符的片 |
| 进度 | 总进度 = Σ 各片已下载 / 总长度，保证单调不减、不超 1 |
| 失败降级 | 单片失败重试该片；整体失败则**回落单连接**（保证不比现在差） |
| 取消/暂停 | 所有片协程挂在同一父 Job 下，取消即全部停止；元数据落盘供下次续传 |

**先写单测的纯逻辑**（配合已建好的测试设施）：

### 第十五轮：多线程分片下载 第 2 步 —— 实现并接入（2026-09-12）

**做了什么**（新增代码全在 `core/data/.../data/download/segmented/`，接入只动 `DownloadExecutor` 内部）：

| 新增 | 作用 |
|---|---|
| `ContentRange` | 解析 206 的 `Content-Range`（纯函数），用来核对"回给我的确实是我要的那一段" |
| `SegmentResumePlanner` / `PartResume` | 把「计划 ＋ 边车」翻译成「每片本次从哪个**绝对偏移**写起」 |
| `RemoteFileProbe` | HEAD 取长度与 `Accept-Ranges` |
| `SegmentedDownloader` | 并发分片下载主体（`RandomAccessFile` 定位写 ＋ 边车元数据） |
| `SegmentedTempFileReconciler` | 回落单连接前，把临时文件整理成"单连接能安全接手"的状态 |

`DownloadExecutor` 里：探测 → 尝试分片 → 成功即重命名（沿用原有 `.downloading` → 正式文件的约定）；
失败/不适用就整理临时文件，然后走**原有单连接逻辑（那一行都没改）**。
开关 `SEGMENTED_DOWNLOAD_ENABLED = true`、并发 `DEFAULT_CONCURRENCY = 4` 目前是常量，第 3 步再接设置项。

**三条"写坏文件"级别的保命规则**（每条都有测试 ＋ 变异验证）：
1. **只在 206 上写**：发了 `Range` 却收到 200（服务端忽略 Range、把整份发来），
   再按片偏移写就把文件彻底写乱 → 直接放弃分片；
2. **核对 `Content-Range` 起点**：回的段不是我请求的那一段，就拒绝写入；
3. **写入严格截断在片尾**：服务端多发的那部分属于下一片，收下就污染邻片；
   反过来 body 被截断（少发）**绝不能算成功**，要重试该片。

**两个不显眼、但不做就会静默损坏的点**：

- **回落单连接前必须截断临时文件**。单连接是按「文件长度」判断已下载量的，而分片是各片
  乱序 `seek` 到绝对偏移写的（文件长度可能已经等于全长、中间却还有洞）。必须按边车算出
  「从片 0 起真正连续的字节数」，把文件截到那里再回落 —— 否则单连接只补后半段，
  产出**长度全对、内容错位**的文件。这就是 `SegmentedTempFileReconciler` 存在的唯一理由。
- **`matches()` 补上"自身声明的总长"校验**。原来只比片数与边界，一份"边界对、总长却写着别的数"
  的自相矛盾元数据也会被信任；写入偏移正是靠这些字段算出来的，不能只挑"看着还行"的字段用。

**为什么"放弃分片"不用抛异常去中止兄弟协程**：让子协程抛异常中止同级协程，要经过结构化并发的
取消转换 —— 在 catch 处看到的可能是 `CancellationException` 而不是原始异常，于是
**"协议不支持"会被误判成"用户取消"**，把一次普通失败变成任务被取消。改成**共享
`AtomicReference` 中止标志**：发现问题的那片记下原因，别的片在读写循环里主动退出，
全程**没有任何异常离开子协程**；而外部取消仍然是真正的 `CancellationException`（暂停/取消语义不变）。

**与第十四轮方案的差异（只有一处，有理由）**：触发条件里"HEAD 声明 `Accept-Ranges: bytes`"
放宽成"**未声明也允许尝试**，只有明确回 `none` 才不分片"。理由：很多 CDN 并不在 HEAD 里声明它，
而现有断点续传本来就在用 `Range` 且能工作；真有服务端不支持，第一条保命规则会当场发现并回落，
代价只是多一次请求。

**第 2 步踩到的坑（都值得记）**：

1. **本机跑单测必须先设 `LC_ALL=C.utf8`**，否则报 `Internal compiler error`。

   `.class`，路径编码不了：
   `InvalidPathException: Malformed input or input contains unmappable characters: …$HEAD 能读到长度与 Accept-Ranges$1.class`。
   两个要点：① 光在命令行设不管用 —— Gradle 守护进程复用旧环境，要先 `sh gradlew --stop`；
   ② 这是**本机环境**问题，CI 是 UTF-8 所以从没暴露 —— "本地红、CI 绿"这种反直觉情况又多了一种。
2. **"进度到 1"这种断言可能是空的**：成功时会**无条件补报**一个 `onProgress(1f)`，
   所以"进度只按第一片算"这个变异照样能过。改成断言**中途**取值必须扫过 0.5
   （4 片里任何单片最多只贡献 1/4）才抓住。教训与 wbi 那次同源：
   **断言要盯住被验证的那个性质，别被无关的兜底行为满足**。
3. **变异本身要检查是不是"有效变异"**：有一条变异（删掉 `contentRange != null` 判断）直接**编译失败** ——
   因为后面的 `contentRange.start` 依赖那处空值检查提供的智能转换。**编译失败的变异不能算"测试抓到了"**，
   要换成等价但能编译的写法（`… && false`）重跑。
4. **`ktor-client-mock` 的 `headersOf`**：可变参数那个重载收的是 `Pair<String, List<String>>`，
   传 `Pair<String, String>` 编译不过（报"没有匹配的重载"）；要么 `name to listOf(value)`，要么用 `HeadersBuilder`。

**顺带修掉一条既有的静默损坏路径**：`RemoteFileProbe` 只在**响应成功**时才相信 `Content-Length`。
改造前不看状态码 —— HEAD 拿到 403/404 时，错误页的 `Content-Length` 会被当成远端文件大小；
一旦它小于本地残留的临时文件，"文件已完整"的判断就成立，于是把**半截文件当成品**重命名过去。

**另一处有意为之的行为变化（日志口径）**：`开始下载: … CDN主机=…` 从"每次尝试一行"改成

与文档里"每次下载一行"的初衷一致。

3. **一次下载只读一次设置，全程复用**。中途改设置不该影响正在跑的任务；
   更要紧的是**回落时整理临时文件必须用同一个分片计划**，否则算出来的"连续前缀"

### 第十八轮：「自动解析链接 → 下载视频」全链路审查 ＋ 第 1 批修复（2026-09-12）

**做法**：对全链路做了一次审查（剪贴板识别 → 解析 → 建任务 → 队列 → 下载 → 合并 → 落盘），
证据分三级：① **真机复现**（系统 `am_crash` 事件）；② **跑真实代码的单元探针**；
③ 逐行读码（另派三个只读子代理并行深挖，它们的结论逐条复核过，下面标注了被修正的地方）。
产物是一份 30 条的清单，**分两批修**；本批（第 1 批）只修「崩溃 + 取毒 + 元数据」三条，
外加把 ffmpeg 命令构建抽成可测的纯函数。

#### 第 1 批修的三条

**① 剪贴板里 `av`/`ss`/`ep`/`space` + 超长数字 → 崩进程（已真机复现）**
`AsRegexUtil` 用 `toLong()`、`handleUserSpace` 也用 `toLong()`，都没有溢出保护；两处调用点
（`ClipboardAutoHandler` 的 `LaunchedEffect`、`AnalysisViewModel` 的 `debounceJob.collect`）
都没有 try/catch → 异常直达 `AppCrashHandler` → 起崩溃页 + `killProcess`。
真机复现（把剪贴板设成 `av1234567890123456789012345` 后启动 App）：
```
16:54:02.375 am_proc_start: com.whyd9527.bilibilias
16:54:02.744 am_crash: [19019,...,java.lang.NumberFormatException,
             For input string: "1234567890123456789012345",Long.java,740,0]
16:54:02.819 am_proc_died: [0,19019,com.whyd9527.bilibilias,200,2]
```
**剪贴板任何 App 都能写**，所以这是外部可触发的崩溃。修法：`toLongOrNull()`（`parse` 与
`handleUserSpace` 各一处），并且 `UserSpace` 的 uid 也要求能放进 `Long` —— 垃圾输入要在
**识别阶段**就被拒掉，否则会先清空用户剪贴板、再发一次注定失败的请求。

**② 链接识别过宽 → 非 B 站文本被判成 B 站链接（实测）**
`ss([0-9]+)`、`(?<=(av|…))([0-9]+)` 没有边界也不看域名：`https://example.com/nav123456`
→ `AV(123456)`；`会议记录 ss123 已上传` → `SS(123)`；`css2024.jpg` → `SS(2024)`。
代价不只是认错：`ClipboardAutoHandler` 会因此**清空剪贴板**、跳到解析页，并展示/允许下载一个
**不相关的视频**（`av1`、`av123456` 都真实存在）。修法是两条：
- 混杂文本里抽 ID 要求**带 B 站域名**（`bilibili.com`/`b23.tv`/`bili2233.cn`），
  否则要求**整串就是那个 ID**；BV 例外（形状够特殊，允许"文案里夹 BV 号"）；
- 每个关键字加左边界 `(?<![A-Za-z0-9])`（`nav12345`、`css2024`、`ABV…` 都不再命中）。

> 有意的取舍：`视频 av170001 很好看` 这种"句子里夹 av 号、又没带链接"的输入现在**不识别**。
> 相比"漏认"（再贴一次链接即可），"误认成另一个视频并下载下来"更糟 —— 这条写进了 `AsRegexUtil` 注释。
>
> 顺手修掉两个小问题：短链只认 `https://` → 改成 `https?://`；正则里的 `[A-z]` 是经典笔误
> （ASCII 65..122 会连带匹配 `[ \ ] ^ _ \``）→ 改成 `[A-Za-z]`。

**③ ffmpeg 元数据被字符串化 → 标题/简介含英文双引号时合并必然失败**
`FFmpegKit.executeAsync(命令串)` 会把命令串交给 `parseArguments` 重新分词，而它只按空格切分、
`"` 只切换「引号内」状态、**不处理 `\"` 转义**。于是 `title="a"b c"` 被切成三个参数 →
合并必然失败；而子任务文件此时**已经完整**，重试会被「文件已完整」的早退分支跳过，
只再合并一次、再失败一次 → **这个视频永远下不下来**。原来那个 `escape()` 是死代码（全仓无调用），
就算接上也没用（它靠 `\"` 转义，而解析器不认）。
修法：改用 `FFmpegKit.executeWithArgumentsAsync(String[])` —— **已用字节码确认**该路径走
`FFmpegSession.create(String[])`、**完全不经过 `parseArguments`**，参数原样传给 native 侧；
同时把命令构建抽成库模块里的纯函数 **`FfmpegCommandBuilder`**，元数据以**单个 argv 元素**
（`title=值`）给出，不再手工拼引号。

1. **[高] 暂停→继续之后队列不再有生命周期**。`resumeTask` 原先自己置 `isDownloading = true` ——
   而那个标志的语义是"队列循环正在跑"，只该由 `startDownloadQueue` 设置。自己置上之后：
   ① 循环其实不存在（暂停时它已退出并解绑服务），任务跑完没人再推进队列；
   ② `addDownloadTask` 看到 `isDownloading==true` 就**跳过启动服务** → 之后新增的任务永远停在
   「等待中」；③ `onDownloadFinished()`（全仓唯一会 `stopForeground` 的地方）再也不会被调用 →
   **「缓存通知」永久常驻**，只能杀进程。
   现在 `addDownloadTask` 与 `resumeTask` 都走**同一个入口** `ensureQueueRunning()`
   （在跑就叫一次循环，没跑就启动服务），再也不存在"标志是 true、循环却不在"的状态。
2. **失败任务静默跳过**：去重只比 `platformId`，于是同一视频失败（ERROR）后再点下载，
   新任务被当成"已在队列里"直接跳过，界面却仍然弹「已添加到下载队列」。
   现在 `mergeTasks` 把 **ERROR 视为"可以重下"**并**替换**旧条目（替换而不是追加，
   是为了保证 `platformId` 唯一 —— 下载列表拿它当 Compose key，重复会直接崩）。
3. **`_downloadTasks` 读-改-写**：`updateTaskState`/`removeTaskFromList` 改成 `MutableStateFlow.update {}`（原子）；
   `processDownloadTree` 不再"拿旧快照 → 做几秒网络调用 → 整份写回"（那会把窗口期内进度回调的更新抹掉、
   甚至把已完成的任务复活成 DOWNLOADING），而是**先在本地建出这一批、最后原子合并**。
4. **选任务与并发上限的 check-then-act**：`checkAndStartNextDownload` 的"读 activeDownloadJobs → 挑任务 →
   写 activeDownloadJobs"中间隔着一次 `launch`，被队列循环 / 每个 Job 的 finally / resume 三条路径
   并发调用时可能挑中同一个 segmentId → 同一文件两个协程双写（产物损坏），且 `[id] = job` 覆盖后
   "取消"只取消得掉后一个。现在整段进 `synchronized(queueLock)`，占位在锁内完成。

另外 `pauseTask`/`resumeTask` 改用规则里的 `canPause`/`canResume`（顺手把"只有下载中能暂停、
合并中不可中断"这条隐含规则写进注释，免得 `pauseAllTasks` 那种"过滤器含 MERGING 但 pauseTask 拒收"的
自相矛盾再出现）。

**验证**：`:core:data` 单测 80 → **95**（+15 规则测试）；变异 **16 → 19 条全部被抓到**；
`:app:compileAlphaDebugKotlin` 通过；CI 全绿。

### 第二十三轮：第 3 批 C —— 无媒体记录的显示 / 提前写 COMPLETED / 空封面 URL（2026-09-12）

**① 「已完成下载」里没有媒体文件的记录显示成「音视频 / 未知画质 / mp4」（观感，你选的方案 3）**

改法：新增 `core/data/.../data/download/record/DownloadRecordDisplayRules.kt`（纯规则，可单测）：

| 函数 | 作用 |
|---|---|
| `hasMediaFile(savePath)` | 判据是 `savePath` 是否为空 —— 正常完成时它一定是 `content://` URI 或文件路径（`handleSuccessor` 移动成功后才写），而没有媒体文件那条路径**刻意保持为空** |
| `tags(modeTitle, qualityTitle, extension, savePath)` | 有媒体文件 → 模式/画质/封装（原样）；没有 → **只显示「仅附加内容（无媒体文件）」一个标签** |

**② 单子任务下载成功后就地写 COMPLETED（第十八轮）**

`downloadSingleSubTask` 原先在这一步就把内存 ＋ DB 都写成 COMPLETED，但那时
①产物还在私有目录（合并与移动都还没跑）、②`savePath` 指的是临时文件。后果是**DB 与界面分裂**：
合并/移动一旦失败，`failTask` 只改内存态，**DB 那行永远停在 COMPLETED** ——
完成列表里留下一条指向私有临时文件的假记录，重启后还会被 `initDownloadList` 当"已完成"保留。

改法：那个写入整段删掉，**COMPLETED 只留一个入口** —— `handleSuccessor` 里**移动成功之后**那一次
（第二十一轮已经把 DB 写入挪到移动之后了，这次是把它变成唯一入口）。
子任务下载完只返回结果，状态由进度回调自然推进（DOWNLOADING → MERGING → COMPLETED）。

> ⚠️ **这条没有单测可配**：它是一个"谁有权写终态"的**行序**问题，主体在 `:app`。
> 能验的是：① 编译；② 真机上单子任务（仅音频/durl）下载仍然正常完成、完成列表没有多余条目。
> "移动失败会留下假记录"这条本身**真机造不出来**，只能靠"COMPLETED 只有这一个入口"来保证。

**③ 封面为 null 时请求空 URL → 整集下载失败（第十八轮）**

`handlePredecessor` 的内嵌封面与 `downloadCoverImageForTask` 都用 `task.cover?.toHttps() ?: ""`

改法：新增 `core/data/.../data/download/predecessor/DownloadPredecessorRules.kt`：

### 第二十四轮：第 4 批 —— 重启清理 / Service 生命周期 / 取消 ≠ 失败（2026-09-12）

三条，都是"进程/会话边界上留下的坏状态"。

**① 重启后：PAUSE 幽灵 ＋ WAITING/ERROR 被静默删除 ＋ 失败任务临时文件永不清理（第十八轮）**

原先 `NewDownloadManager.initDownloadList()` 只有一行判断：
`if (state !in listOf(PAUSE, COMPLETED)) deleteSegment(...)`。三个后果：

- **PAUSE 变幽灵**：行留在 DB 里，但重启后内存任务列表是空的 —— 界面不显示它，
  `resumeTask` 也找不到它（它按 segmentId 在内存列表里找），用户既看不到也恢复不了；
- **WAITING/ERROR 被静默删除**：失败过的任务连记录都不剩，用户不知道为什么没了；
- **失败任务的 `.downloading` / `.downloadpart` 永不清理**：只删 DB 行，不碰文件。

改法：新增 `core/data/.../data/download/startup/DownloadStartupRules.kt`（纯规则，可单测）：

| 处理方式 | 状态 | 含义 |
|---|---|---|
| `KEEP` | `COMPLETED` | 保留，出现在「已完成下载」里 |
| `DISCARD_KEEP_FILES` | `PAUSE` / `WAITING` / `PRE_TASK` / `DOWNLOADING` / `MERGING` / `POST_TASK` | 丢记录（不再有幽灵），**保留**中间文件 —— 下次添加同一内容时 `Range`/分片边车能接着下 |
| `DISCARD_AND_CLEAN` | `ERROR` / `CANCELLED` | 丢记录，**并删掉**中间文件（已经终结，残留没意义） |

临时文件按**文件名前缀** `<platformId>_` 认领（`createSubTask` 定死的命名），
`.downloading` 与 `.downloadpart` 边车一并覆盖；丢弃过东西会打一行日志并**弹一次提示**
（`已清理 N 个上次未完成的下载`），不再静默。

> ⚠️ **为什么不是"把 PAUSE 恢复成可继续的任务"**：跨重启续传需要用户当初选的那套质量参数
> （`DownloadViewInfo` 的 selectVideoQualityId / selectVideoCode / selectAudioQualityId），
> 而它**没有落盘**（`segment.platformInfo` 存的是平台的 page/episode JSON，不含选择）。
> 拿猜出来的参数去续写一个已经下了一半的临时文件，会写出**长度对、内容却来自另一条码流**
> 的坏文件 —— 正是本项目最怕的那类静默损坏。所以宁可不去恢复，也不猜。

**② `DownloadService`：`START_STICKY` ＋ 从不 `stopSelf()`（第十八轮）**

- `onStartCommand` 返回 `START_STICKY`：进程被杀后 Android 会用**空 intent** 把服务再拉起来 →
  又走一次 `startForeground()` → 留下一条 **0% 的「AS视频缓存中…」通知**，
  而这时队列根本不存在（管理器状态随进程没了），通知会一直挂着，只能杀进程。
  → 改成 **`START_NOT_STICKY`**（真正在下的任务由用户重新添加即可，服务不需要复活）。
- `onDownloadFinished()` 只 `stopForeground(REMOVE)`：通知没了，但服务仍是"已启动"状态
  （它当初是被 `startForegroundService` 拉起来的），不 `stopSelf()` 就一直挂着、进程也随之常驻。
  → 补 `stopSelf()`，并在 `onDestroy` 里兜底撤通知。

**③ 取消被记成"下载失败"并弹提示（第十八轮）**

`DownloadExecutor` 的重试循环与读写循环都写着 `catch (e: Exception)` —— 而
**`CancellationException` 也是 `Exception`**。于是用户在下载途中点「暂停」/「取消」时：
被吞掉 → 当成一次"下载异常" → **白重试 5 次**（每次都在已取消的协程里立刻失败）→
返回 false → 上层记成"文件下载失败（已重试 5 次）" → **任务变 ERROR 并弹「下载失败」**。
用户明明是自己按的取消，界面却报失败；而且这条 ERROR 会被队列当成"可以重下"的状态，语义整个乱。

改法：新增 `core/data/.../data/download/cancel/DownloadCancellationRules.kt`（纯规则，可单测）——
`isRetryableFailure(e)` 为 false 就**原样抛出**，两处 catch 的第一件事都是它。
规则还会**顺着 `cause` 链**看（取消常被包一层：`RuntimeException("下载流读写异常", CancellationException)`），
只看最外层会让同一个 bug 换个形状复发。

> 顺带记一下：分片路径（`SegmentedDownloader` / `RemoteFileProbe`）**本来就有**
> `catch (e: CancellationException)` 排在 `catch (e: Exception)` 前面，所以这个洞只在单连接路径上。
> 这也解释了为什么第十九轮真机测"暂停→继续"时看起来是好的（那次是大文件走分片）。

**验证**：`core:data` 单测 **115 → 125**（+10）；变异 **31 → 36 条全部被抓到**（新增 32~36）；`:app:compileDebugKotlin` 通过；推送 `72ec0667`，CI 全绿。

**⚠️ 真机验证时又抓到两条"代码写对了、但根本没生效"的问题（已修，推送 `0e2aaf09`）**

真机跑第 ① 条时发现：**重启后一行清理日志都没有**（先核对了设备上已安装 APK 的 sha256，
与 CI 产物逐字节相同，确认装的确实是这一版 → 不是装错包）。查下来两条：

1. **`initDownloadList` 读 DB 用的是 `getSegmentAll().last()`，而它是 Room 的热流**：
   Room 的 `Flow` 先发一次当前结果、之后只在表变化时再发，**永远不会 complete**；
   而 `last()` 的语义是"等流结束取最后一个" → **永远挂住**。
   也就是说这段"启动清理"**从实现那天起就没有执行过一次**（第十八轮审查是读代码得出的清单，
   把"会删"当成事实，实际它只是死代码 —— 这也是"WAITING/ERROR 被静默删除"那条的真相：

   ＋ `FlowReadOnceTest` 把 `first()`/`last()` 在"不会结束的流"上的区别钉住（变异 37）。
2. **`failTask` 只改内存态、不写 DB**：于是失败任务的 DB 行永远停在 `WAITING`，

   （光有第 ① 条的状态映射还不够）。修法：失败态一并落盘，顺手也修掉"DB 与界面分裂"。

### 第二十六轮：第 5 批 —— 重复记录 / 落盘顺序 ＋ 修掉一个会随机红的测试（2026-09-13）

两条（第十八轮清单剩下的中危项，它们是同一个病根：**重新下载同一集**）。

**① 同一集被重新下载会插出第二条同 `(nodeId, platformId)` 的记录**

`DownloadTaskRepository.createSegment` 原先写的是：已有记录且**已完成** → 返回 null →
**再插一条新的**。而落盘文件名是命名规则算出来的（同一集必然同名），
后一次下载会覆盖前一次那个文件 —— 于是**第二条记录永远指向一个不存在的文件**：
「已完成下载」里出现两条同名条目，其中一条点开是"文件不存在"。
（第二十四轮真机时 DB 里就积了 **3 条**未完成记录，正是多次重复添加攒出来的。）

改法：新增 `core/data/.../data/download/record/DownloadRecordReuseRules.kt`（纯规则，可单测）：

| 函数 | 作用 |
|---|---|
| `persistAction(hasExistingSegment)` | 一个 `(nodeId, platformId)` **只允许一条**：有就复用，不再插新的 |
| `stateWhenReused(previous)` | 复用时把状态改成什么 —— **已完成的那条必须重置为 `WAITING`** |
| `stagingFileName(finalName)` | 落盘用的临时名（见 ②） |
| `canDeleteExistingFile(newFileWritten)` | 什么时候允许删同名旧文件（见 ②） |

> ⚠️ 那条 `WAITING` 重置不是可有可无的：复用出来的任务若带着 `COMPLETED` 进内存列表，
> 而队列只挑 `WAITING`（`DownloadQueueRules.nextTaskIndex`）→
> **用户点了下载会永远停在"已完成"、什么都不发生**。

**② 移动成品进下载目录时"先删同名旧文件、再写新文件"**

`FileOutputManager` 两条路径（MediaStore / 旧版文件系统）都是先删后写：
中途失败（空间不足、被占用、MediaStore 拒绝）就会**把用户已有的那个文件弄没了**，
而新的又没生成 —— 净效果是"重下一次反而丢了原来的"。

改法（两条路径同一个顺序）：**先用临时名把新文件完整写出来 → 成功之后才删同名旧文件 → 再改名**；
任一步失败就回滚新文件，**旧文件原样不动**。
MediaStore 那条路径顺带修掉两个细节：
- 只删"查到的那一条"→ 改成**全删**同名（旧版本重复下载会攒下多条同名记录，
  只删一条会留下"同名但没记录"的残留文件）；遍历游标时先收 id 再删（边遍历边删会让游标失效）；
- 改名（`resolver.update` 改 `DISPLAY_NAME`）失败不算致命：保留临时名并打日志，文件照样能打开。

> 📌 **诚实标注**：②的"失败回滚"**真机造不出来**（要存储不足/目录被占用/MediaStore 拒绝）。
> 能验的是：正常路径不回归、下载目录里不会出现 `.part` 残留、同名旧文件被正确替换；
> "失败时旧文件保住"只有规则单测（变异 40/41）＋ 代码顺序保证。

**③ 顺手修掉一个"会随机红"的测试**（第二十二轮留下的）

`AnalysisInputPipelineTest` 第一版用固定 `delay(400)` 去等防抖结果 —— 而它要验的正是**真实时间**行为，
于是受机器负载影响：变异跑手刚结束、Gradle 守护进程还忙时，头一次解析还没发出来第二次就提交进去了，

### 第二十八轮：第 6 批 —— 单连接续传写模式 / Compose key（2026-09-13）

**① 单连接回落遇「要 Range 却回 200」会按追加写（第十八轮清单里最后一条中危）**

`DownloadExecutor.performDownload` 只要临时文件里已经有内容，就会发
`Range: bytes=<已下载>-`，并且**无条件以追加模式打开文件**
（`FileOutputStream(tempFile, append = true)`）。而服务端完全可能**忽略 Range、回 200 + 整份文件**：
这时"追加"就把整份内容接到了半截文件后面 —— 产出**长度翻倍、内容错位**的坏文件，
而且照样报"下载成功"。分片路径早就防了这条（"只在 206 上写"），单连接这条一直没防。

改法：新增 `core/data/.../data/download/resume/SingleConnectionResumeRules.kt`（纯规则，可单测）：

| 判据 | 结论 |
|---|---|
| 没发 Range（起点 0） | 从头写 |
| **要了 Range 却回 200** | **从头写**（服务端把整份发来了，绝不能追加）← 这条就是那个 bug |
| 206，但 `Content-Range` 起点 ≠ 我请求的起点 | 从头写（偏移不对） |
| 206，起点对得上（或没给 `Content-Range`） | 追加 |

接线时**进度起点与总长也按这个结论算**（否则"从头写"时进度会从半截开始、总长会被多算一次），
并在"服务端没按 Range 回"时打一行日志说明丢弃了多少已下字节。

**② `DownloadScreen` 用 `platformId` 当 Compose key**

`items(downloadListState, key = { it.downloadSegment.platformId })` ——
`platformId` 是"哪一集"的标识、不是"哪条记录"的标识，列表里一旦出现两条同 `platformId`，
Compose 会因为**重复 key 直接崩**。第 5 批已经把"重复 segment"的产因修掉了，
但 key 本身也该选对：换成 `segmentId`（数据库主键，天然唯一）。

**② 命名规则 `Regex("_+")` 会把标题里的下划线吃掉（第十八轮）**

原 `NamingConventionHandler.buildFileNameWithConvention` 每替换一个占位符就对**整个累计字符串**

"某个占位符取值为空、留下多余分隔符"兜底的（`p_title` / `collection_*` 经常是空串），

把模板按占位符切成「模板字面段 / 取值段」，**只对模板字面段塌缩**，取值一个下划线都不动：

| 段落 | 处理 |
|---|---|
| 模板字面段（`_`，来自用户模板） | 段内连续下划线塌成一个（老行为） |
| 取值段 | 原样保留 |
| 取值为空 | 不产出字符，只吃掉**紧邻的那一个**分隔下划线 |

抽到库模块的理由和以前一样：`:app` 的单测本机跑不了（aapt2 是 x86_64），
而这条不变量（"值里的下划线是内容"）只有单测钉得住。

> ⚠️ **一次被自己推翻的修法（值得记）**：第一版想的是"把每个取值用哨兵符 `\u0001` 整段围住，
> 再对整串 collapse" —— **不成立**。Java/Kotlin 的 `replaceAll("_+", "_")` 把相邻匹配
> 当成各自独立的一次替换，`\u0001A__B\u0001` 里的两个 `_` 仍然各自被替换掉，值照样被塌
> （我先在 JVM 里单独验了一遍才发现的）。所以只能改成**结构上分段**，不靠转义技巧。

**③ `getSegmentBvId` 靠"解码必然抛异常"兜底（第十八轮）**

原写法（`VideoInfoFetcher`）：
```kotlin
try { platformInfo["bvid"] as? String } catch (e: Exception) { …按 nodeId 反查… }
```
而 `platformInfo` 对普通视频页存的是 `BILIVideoViewInfo.Page`（**没有 `bvid` 字段**）、
对番剧集存的是 `BILIDonghuaSeasonInfo.Episode`（`bvid` 可空）——
`decodeFromString` 这两种都**正常返回**，`as? String` 只是得到 null，**根本不抛异常**，
所以"按 nodeId 反查"那条兜底**一次都没执行过**。而且一旦哪天 JSON 真的解不出来，
走进的也是与"没有 bvid"完全无关的分支 —— 两种语义挤在同一个 catch 里。

改法：新增 `core/data/.../data/download/bvid/DownloadBvIdResolver.kt`（纯规则）——
三条候选各自独立判断，不再拿异常当分支：

1. 子任务的 `platformId`（合集章节里的分 P）；
2. `platformInfo` **显式**有 `bvid` 字段 → 用它（**字段存在但为空 = 明确没有**，不再往下兜底）；
3. 都没有 → 所属节点的 `platformId`（**这条是这次补上的兜底**）。

顺带：候选值只认**真正 BV 号的形状**（`^BV[0-9A-Za-z]{10}$`），所以节点 `platformId`
是数字（章节 / 季度 ID）时不会被当成 bvid 发出去；`VideoInfoFetcher` 里那个
**从未被用过的 `Json` 注入**也一并删掉（它唯一的用途就是那个 try 里的解码）。
另外加了一行**长期保留的取证日志** `ASVideoInfo: bvid 解析: …`，真机 grep 即可看到
"解析出了哪个、从哪来"。

**④ 内嵌封面 / 字幕的缓存文件不清理（第十八轮）**

合并阶段要先把封面与字幕落成临时文件再把路径交给 ffmpeg：

`externalCacheDir/cc/embed_cc_<segmentId>_<lan>.srt`。这两个目录**只有**

下一集又是新文件（segmentId 不同），攒着不清理，用户也不知道该去清。

改法：新增 `core/data/.../data/download/cache/EmbedCacheRules.kt`（纯规则）＋两处接线：

| 时机 | 行为 |
|---|---|
| 启动扫一次（`sweepEmbedCacheDirs`） | 这两个目录里所有 `embed_` 开头的文件都删掉 —— 此刻没有任何合并在跑，都是上次会话的残留 |

—— 目录里同时躺着别的任务的临时件也不会被误删。

## 七、常用操作

### 推送代码（这台设备专用）

`github.com` 在本机被阻断（`api.github.com` 正常），所以不能用 `git push`，
要用脚本走 API：

```bash
GH_TOKEN=<你的token> python3 /sdcard/MT2/bilibilias/tools/push_via_api.py
```

Token 权限只需两项：**Contents** 和 **Workflows**（都选 Read and write）。
脚本会逐文件比对本地与远程（比对 git blob SHA **和权限位**，**不依赖 commit SHA 是否一致**），
内容没变就不会产生空提交，有改动才推送。

> `Workflows` 这项别漏：只要这次推送碰到 `.github/workflows/` 下的文件，
> 缺它就会被拒，报错里带 `without workflow scope`。

常用参数：

```bash
# 只看差异，不写远程（公开仓库免 token 也能跑，用来确认"改了什么"）
python3 tools/push_via_api.py --dry-run

# 新文件还没 git add 时，一次性纳入
GH_TOKEN=xxx python3 tools/push_via_api.py --stage-all -m "feat: xxx"
```

> 顺带一个反直觉但重要的事实：**走 API 推送后，远程的 commit SHA 和本地永远不一样**，
> `git status` 里 `origin/main: gone`、本地 HEAD 与远程对不上，都是正常的，
> 不代表有改动。判断"是否真的没改"要用上面的 `--dry-run`（它比 blob SHA）。

## 八、踩过的坑（避免重犯）

1. **绝不用 `git checkout -- .`** 恢复文件！它会连你**未暂存的修改一起回滚**。
   手机上图片会被系统清理，正确做法是只恢复被删的那个文件：
   ```bash
   git status --short | awk '$1=="D"{print $2}' | while read f; do git checkout -- "$f"; done
   ```
2. **Android 字符串资源里不能有裸撇号**（如 `Bilibili's`），
   aapt2 报 `Invalid unicode escape sequence` 直接构建失败。
3. **批量替换要防误伤标识符**：我曾把 `BILIBILIAS` 全局替换成中文，
   结果 `BILIBILIASTopAppBarStyle` 也被改坏。
4. **改完必须先核对再提交**：`grep` 确认关键改动确实写进文件了。
5. **Kotlin 不强制目录与包名一致**，所以包名重命名光靠"编译通过"验证不了，
   要额外核对 package 声明与目录路径。
6. **不要靠猜，先拿证据**：这一轮修 bug 时我猜错过两次方向，
   后来加日志探针（`TAG=ASDialog` / `ASDownload`）一次就定位了。
7. **重写签名/加密代码时，逐步比对"派生过程"，不能只比对常量**：
   我比对了 64 项置换表、CDN 关键字、白名单（全部一致），却漏掉 `setKey()` 里的
   `.take(32)` —— 而 wbi 的置换表有 64 项却**只取前 32 项**，漏掉就让**所有 wbi 签名失效**
   （3.1.7 的事故就是这么来的）。**编译与 CI 抓不到这类错误**。
8. **接口返回错误时不要硬解 `data`**：B 站的错误响应（如 `-352` 风控）里的
   `data` 可能是 `{"v_voucher": ...}`，当成成功结构解析会抛
   `Fields [...] are required` 并把原始异常糊到界面上。错误响应应当按 code/message 报错。
9. **本机跑单测必须先 `export LC_ALL=C.utf8`**（还要 `sh gradlew --stop` 让守护进程重起 ——
   它复用旧环境，光在命令行设不管用）。不设的话，只要**测试方法名是中文、方法体里又有 lambda**
   （`runBlocking` / `zipWithNext` 都算），Kotlin 就会去写一个中文名的 `…$方法名$1.class`，
   而本机 `sun.jnu.encoding=ANSI_X3.4-1968` 编码不了这个路径 → 表面报
   `Internal compiler error`（真正的错因 `InvalidPathException: … unmappable characters`
   藏在 `--stacktrace` 里）。**CI 是 UTF-8，所以只有本机会中。**
10. **断言别被"无关的兜底行为"满足**：分片下载成功时会无条件补报一个 `onProgress(1f)`，
    于是"进度只按第一片算"这个变异**照样能让"进度到 1"的断言通过**。
    必须改成断言**中途**取值（4 片时中途必须扫过 0.5）才抓得住。
    与第 7 条同源：**先想清楚"哪条断言真的能区分对错"，再去写它**。
11. **变异验证要先确认"这是个有效变异"**：有一条变异让代码直接编译失败 ——
    这种**不能算"测试抓到了"**（测试根本没跑）。要么换等价但能编译的写法，要么承认它无效。
    同理：**改了配置/依赖之后要把变异重跑一遍**，别拿上一轮的结果当结论。
12. **`mutation_check.py` 跑的时候会临时改写生产代码**（跑完才还原）——
    所以它跑的过程中**绝对不要推送、也不要编辑它列出的那些文件**。
    第二十一轮我就差点把一份"正被注入 bug"的 `SegmentedDownloader.kt` 推上远程：
    信号是 `git diff --stat` 里突然多出一个我根本没改过的文件。
    要推送就等它跑完，并顺手确认 diff 里没有"意料之外的文件"。
13. **推送前先 `--dry-run`，并且要看"未跟踪文件"那一段**：新文件不会被自动纳入，
    漏掉就会推一个"引用了不存在文件"的提交（CI 直接编译失败）。加 `--stage-all` 兜住。
14. **从 CI artifact 里只要一个 APK：用 HTTP Range 取，别下整包**（第二十一轮真机验证时用的）。
    跑手已经进仓库：`python3 tools/fetch_ci_apk.py <token> <run_id> arm64-v8a 输出.apk`。
    artifact 是 139MB 的 zip，里面 4 个 APK 只有 arm64-v8a 那个（38MB）真机用得上：
    读末尾 64KB 找 EOCD → 读中央目录 → 按偏移只取那一个条目的数据段 → `zlib.decompress(blob, -15)`。
    全程 43 秒、约 20MB 流量（整包要 139MB）。两个坑：
    - GitHub 会 **302 到 Azure Blob 的 SAS 地址**，而**不能把 `Authorization` 头带过去** ——
      SAS 签名 + Authorization 头会被一起拒（`401 Server failed to authenticate`）。
      要自定义 `HTTPRedirectHandler`，在 `redirect_request` 里把该头删掉。
    - 这条链路会**中途断流**（`IncompleteRead`，第一次跑就撞上）：按 2MB 分块取、逐块重试。
15. **真机验证时注意 DSHA 的悬浮窗**：用户把 DSHA 挂在**悬浮窗**上时，
    - `/app/ui/dump` 的"当前窗口"经常是 `com.dsh.client`（悬浮窗抢焦点），
      按坐标点击会打在悬浮窗上 —— 等于点了个寂寞；
    - 但**按文字点按走的是无障碍节点的 click 动作，不受遮挡影响**（我这轮就是靠这个
      点到了被悬浮窗盖住的输入框和「点击重试」）；
    - 想拿回焦点：先点一下 App 里**没被悬浮窗盖住**的地方，再 dump。
    还有两条本轮实测到的：`/app/clip` 写剪贴板不需要 App 在前台，**读**剪贴板才需要；
    应用内输入框用 `/app/ui/input` 有时报"输入被系统拒绝"（那一刻焦点在别处），重试即可。
16. **Room 的 `Flow` 上不要用 `last()` —— 它会永远挂住，那段代码等于从来没跑过**（第二十四轮踩的）。
    Room 的 `@Query fun xxx(): Flow<T>` 是**热流**：先发一次当前结果，之后只在表变化时再发，
    **永远不会 complete**。而 `last()` 要"等流结束取最后一个" → 协程永远停在那一行。
    症状极具迷惑性：**编译过、单测（如果有）也可能过、日志里什么都没有**，
    看起来就像"那段逻辑写得不对"，其实是**根本没执行**。
    本项目里 `initDownloadList` 就这么白躺了很久（"启动清理未完成下载"从未生效）。
    正确写法：`first()`（本项目里包成了 `core:data/.../data/util/FlowReadOnce.kt` 的 `readOnce()`，
    配 `FlowReadOnceTest` 钉住差异）。
    > 顺带一条方法论：**审查读代码得出的清单要标明"这是读出来的"**。
    > 第十八轮把"重启会删 WAITING/ERROR"当成事实写进了清单，而真机一验才发现那段根本没跑 ——
    > 结论（"记录会消失"）恰好相反（实际是记录一直留着、谁都看不到）。
17. **容器里看不到 `Android/data`**：`ls /storage/emulated/0/Android/data/<pkg>/files/...` 在容器里
    永远返回"没有这个目录"，`2>/dev/null` 一加就会**误读成"目录是空的"**（我因此写错过一条证据）。
    要看应用私有目录就用**设备 shell**：`/root/dsh-bin/adb-shell "ls /storage/.../files/video"`
    （shell 级可读，实测能看到 `.downloading` 与 `.downloadpart`）。
18. **MediaStore 的 `RELATIVE_PATH` 是带结尾斜杠存的**（`"Download/BiliDownloader/"`），
    而调用方通常写成 `"Download/BiliDownloader"` —— 用 `RELATIVE_PATH=?` 等值查**永远匹配不到**，
    于是"删同名旧文件 / 按目录找文件"这类逻辑会**静默变成 no-op**：不报错、没日志、看起来无害。
    第二十六轮就是这样：`FileOutputManager` 里"删除同名旧文件"从旧代码起从未生效，
    真机表现为重下同一集时旧文件不删、MediaStore 把新文件**自动改名**成 `xxx (1).mp4`，
    每次多攒一份 100MB 级副本。要查就**两种写法都试**（`IN (?,?)`），别赌它存的是哪种。
    同源教训：**"删东西"的代码错了不会报错，只会什么都不删** —— 必须真机看结果，
    或者像这一轮那样在改名后**读回校验**、把异常情况打进日志。
19. **别只信"读代码得出的结论"**：第十八轮那份清单是逐行读出来的，其中两条真机一验就翻了 ——
    `initDownloadList` 的 `.last()` 让它**从未执行**（第二十四轮）、
    这个 `RELATIVE_PATH` 让"删同名旧文件"**从未生效**（第二十六轮）。
    两条的**后果**都和清单里写的不一样。所以清单要标明"这是读出来的"，
    而每批修完必须挑一条能真机触发的路径走一遍。
20. **正则的方言差别：JDK 能跑 ≠ Android 能跑**（第三十一轮真机第一次点下载就崩）。
    `Regex("\\{[a-z_]+}")` —— 右花括号没转义。JDK 的 `Pattern` 接受它，
    **Android 的 ICU 引擎直接报 `PatternSyntaxException: Syntax error … near index 10`**；
    而它写在 `object` 的静态初始化里 → `ExceptionInInitializerError` → 整条下载线程挂掉。
    两个要点：① **两边都转义**（`\\{…\\}`）最稳，别指望某个方言会宽容；
    ② 本机单测跑的是 JDK 正则，**抓不到这类问题**，新写正则的批次必须真机点一次下载。
    同类"本机绿、真机崩"的还有：`:app` 的单测跑不了、资源错误只有 CI 能发现。
    附带一条观测事实：**MIUI 的 logcat 会丢 `Log.d`**（同一轮下载 `ASDownload` 只剩寥寥几行），
    所以"日志里没看到"不能当成"代码没跑" —— 要看结果文件或 UI。

## 九、这台手机的坑（2026-09-12 事后修正：比原先写的严重得多）

原先这里写的是"图片和 APK 会被清理，文本文件没事"。
**这个判断被现实推翻了**，实际被清掉的东西包括：

| 被清掉的东西 | 后果 |
|---|---|
| `/sdcard/Download/BiliDownloader-signing/` 整个目录 | 签名密钥本地副本全灭，只剩 GitHub Secrets |
| `/sdcard/MT2/apks/push_via_api.py` | 推送脚本没了（已重建，并挪进仓库） |
| `.git/objects/pack/*.pack` | **git 对象库被破坏**，历史与当前文件都受影响 |
| 之前下载的 APK、图标、预览图 | 需要重新出包 |

**结论：`/sdcard` 上不存在"安全"的文件类型**，.py / .md / .jks / .git 内部文件都中过招。

**对策（按重要性排序）**：
1. 凡是重要的东西，**第一份副本就要放到 GitHub 或网盘**，别把 `/sdcard` 当仓库。
2. 工具脚本一律放进 git 仓库内（如 `tools/`），跟着代码走，别散落在 `/sdcard/MT2/apks/`。
3. 定期 `git fsck` 体检（见下），别等提交失败才发现对象丢了。

### 2026-09-12 事故与修复记录

**症状**：改完代码 `git commit` 报
`error: invalid object 100644 <sha> for 'ecology/README.md'` / `Error building trees`。

**诊断结果**：
- `.git/objects/pack/` 里的 **`.pack` 数据文件丢失**，只剩 `.idx`/`.rev` 空壳
  → 上游克隆来的历史（302 blob / 150 tree / 3 commit）全部消失；
- 索引引用的 blob 里 **251 个缺失**（就是当前工作区那批文件的 blob）；
- 当前提交可达的 tree 里 **31 个缺失**（`core/database`、`gradle/wrapper`、
  `app/src/main/res/values-v31` 等真实目录）。

**修复做法（全部离线，不需要网络）**：
1. 用工作区内容重建缺失 blob：`git hash-object -w`。

**踩到的四个坑（都值得记）**：

1. **细粒度 PAT 建不了仓库。** `POST /user/repos` 返回
   `403 Resource not accessible by personal access token`，响应头写着
   `x-accepted-github-permissions: administration=write`，而该 token 在已有仓库上
   `admin` / `push` 都是 `true` —— 说明这是**细粒度 PAT 的固有限制**，
   不是"权限没给够"。**建仓库只能用经典 PAT（`repo` scope）或在网页上手工建。**
2. **新仓库必须勾 "Add a README file"（或用 `auto_init: true`）。** 否则是空仓库、
   没有分支，`tools/push_via_api.py` 第一步 `GET /git/ref/heads/<branch>` 就直接失败。
3. **旧仓库一删，Secrets 与 Actions artifact 一起消失。** 这正是"密钥只存在于 Secrets"
   这种设计的真实风险 —— 第六节那句"千万不要删那 4 个 Secret"要按最高优先级对待。
   本次没出事的唯一原因是**当时导出过一份加密备份**。
4. **该 token 没有 `Secrets` 权限**（`GET /repos/.../actions/secrets` → 403），
   所以 CI 的 4 个签名 Secret **只能到网页上手工填**，API 改不了。
   （`GET /actions/workflows` 返回 200，说明 Workflows 权限是有的。）
