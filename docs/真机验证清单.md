# 真机验证清单（每次发版后照着跑）

> 这份清单是 2026-10-01 那轮真机调试的产物：当时的每个坑都对应下面的一条检查。
> **不必全跑**，但 **A / B / C 三组是必跑**（它们覆盖"用户升级会打不开""下完的文件丢了/多份"这两类最痛的后果）。

机型参考：小米 `2510DRK44C`（Android 16 / SDK 36）。其它机型同样适用，但要注意
[文末的四个 ROM 怪癖](#附这台机器上-mediaStore-的四个怪癖)只在这台机器上被完整复现过。

## 0. 准备

1. 覆盖安装新包（同一把签名，**登录状态与设置都不会丢**）：
   ```bash
   adb install -r app-alpha-arm64-v8a-release.apk
   # 或在手机上点 APK 安装
   ```
2. 确认版本与显示名：
   ```bash
   adb shell dumpsys package com.whyd9527.bilibilias | grep -E "versionName|versionCode|lastUpdateTime"
   ```
   - 期望：`versionName` 与 Release 一致；应用名在桌面显示为 **BDT**。
3. 轨迹文件位置（**排查任何"删除/清理没生效"先看它**）：
   ```
   /sdcard/Android/data/com.whyd9527.bilibilias/files/logs/download-trace.log
   ```
   ```bash
   adb shell cat /sdcard/Android/data/com.whyd9527.bilibilias/files/logs/download-trace.log | tail -20
   ```
   > MIUI 会过滤 app 自己的 logcat，所以这个文件是**唯一可靠**的取证渠道。

> ⚠️ 下载目录 2026-10-01 已由 `Download/BiliDownloader` 改名为 **`Download/BDT`**（旧目录不搬移：
> 老文件留在原地、记录仍按绝对路径能打开；**占用统计会把新旧目录一起算**，不会显示成 0 B）。
> 所以验证时以 `Download/BDT` 为准，看到 `BiliDownloader` 里的老文件属正常。

## A. 启动与升级（必跑）

| 步骤 | 期望 |
|---|---|
| 装完新版直接打开 | 能正常启动，**不闪退**（= Room 的 DB 迁移成功；迁移写错会直接打不开） |
| 「下载管理 → 已完成下载」 | 升级前的记录**还在**（数据没被清） |
| 新建一个下载任务 | 能正常建任务（唯一索引没把正常插入挡住） |
| **升级到 DB 5→6**（本轮，`download_segment` 唯一索引） | 能打开；「已完成下载」记录**还在**（迁移先删重复行再建唯一索引；**空表也不许删任何行**，`Migration56SqlTest` 盯着） |
| 同一集先下「仅音频」、再下「仅视频」 | 「已完成下载」里**两条记录**、下载目录里**两个文件**（④ 阶段 1 的核心修复；旧版会互相覆盖只剩一条） |
| 再下一次**同一份产物**（同模式 + 同封装） | **不新增记录**（复用原来那条）、磁盘上也不多出文件；原来那条的 `save_path` 不会被清掉（`insertSegment` 已从 REPLACE 改成 IGNORE） |

> 涉及 DB 版本变更时必须跑这一组。v3.3.0 是 **4 → 5**（`download_task` 加唯一索引）；
> 本轮是 **5 → 6**（`download_segment` 加「产物身份」唯一索引）。
>
> ⚠️ **迁移不是"有测试就不用真机跑"**：v3.3.0 的迁移就在这一组里被抓出过"空任务表时把
> `download_segment` 整表删光"（SQL 的 `NOT IN (空集)` 陷阱），v3.3.2 才修好。
> 迁移的 SQL 语义现在有 `Migration45SqlTest`（真跑 SQLite）钉着，但**升级验证仍然要在有数据的库上跑一遍**。

## B. 下载与交付（必跑）

| 步骤 | 期望 | 怎么看 |
|---|---|---|
| 1. 解析一集并下载 | 完成后下载目录里**只有 1 份**、名字**恰好是正式名**、没有 `.part` | 文件管理器看目录 |
| 2. **换一个音频质量后重下同一集** | 仍然**只有 1 份**、名字仍是正式名、**没有 `xxx (1).mp4`**；新文件的大小/时间戳与旧的不同（证明是新下的那份） | 目录 + 轨迹 |
| 3. 看轨迹 | 出现 `交付前挪开同名旧文件: … 枚举=N 目标=N 成功=N` 与 `交付成功，清理挪开的旧文件: 目标=N 实际删除=N` | `download-trace.log` |
| 4. 产物是否完好 | 能播放、有声音、时长与视频一致 | 播放器；或按下方脚本抽查 MP4 结构 |

**抽查 MP4 结构**（在手机上用 MT 管理器或 Python 都能跑）：

```python
import struct, os
p = "下载目录/xxx.mp4"; f = open(p, "rb"); size = os.path.getsize(p)
def walk(f, s, e, d=0, out=None):
    pos = s
    while pos + 8 <= e:
        f.seek(pos); h = f.read(8)
        if len(h) < 8: break
        sz, typ = struct.unpack(">I4s", h); hsz = 8
        if sz == 1: sz = struct.unpack(">Q", f.read(8))[0]; hsz = 16
        elif sz == 0: sz = e - pos
        if sz < hsz: break
        out.append((d, typ.decode("latin1"), pos, sz))
        if typ in (b"moov", b"trak", b"mdia", b"minf", b"stbl"): walk(f, pos + hsz, pos + sz, d + 1, out)
        pos += sz
top = []; walk(f, 0, size, 0, top)
print("顶层:", [t[1] for t in top if t[0] == 0])          # 期望 ftyp/free/mdat/moov
hdls = []
for d, t, pos, sz in top:
    if t == "hdlr": f.seek(pos + 16); hdls.append(f.read(4).decode("latin1"))
print("轨道:", hdls)                                       # 期望含 vide 与 soun
```

## C. 重复文件检查 / 清理（必跑）

1. 先造一份"重复"：用文件管理器把某集**复制**一份，改名成 `原名 (1).mp4`。
2. 打开 app → **下载管理**：
   - 期望顶部出现 **「发现 N 组重复下载文件 … 去清理」**；
   - 若只有「检查重复下载文件」：点一下（首次会要 `READ_MEDIA_VIDEO` 权限，**必须允许**，否则看不到"不是本 app 拥有"的副本）。
3. 点「去清理」→ 期望列出 `保留：<正式名>` + 副本默认勾选 →「删除选中 (N)」。
4. 点删除：
   - 若副本是**本 app 下载的** → 直接删掉；
   - 若是**别的 App / 上一版安装留下的** → 会弹**系统确认框**（「要允许 BDT 删除这个视频吗？」）→ 允许后才删。
5. 期望结果：目录回到 1 份；卡片消失；轨迹里 `清理重复文件: … 实际删除=n 待用户确认=m`。

> 这一步删除失败（`实际删除=0` 且没有系统弹窗）＝回归，先看轨迹再动手。

## D. 其它回归点（每隔几次发版跑一次）

| 项 | 步骤 | 期望 |
|---|---|---|
| 失败不再静默 | 用系统分享发一段**非 B 站文本**（如 `abc`）给 BDT | 出现 `Error：没有识别出 B 站链接或 ID` 卡片 +「点击重试」，点重试会重新解析 |
| 分享入口 | 从 B 站 App 分享一条视频链接到 BDT | 链接自动进输入框并解析成功 |
| 剪贴板门槛 | 未同意隐私政策时启动 | **不读剪贴板、不请求 GitHub**（可用 GitHub 限流计数或抓包核对） |
| 取消/暂停 | 下载中途暂停再继续、取消 | 不应被记成「下载失败」；恢复后能接着下 |
| 抽帧工具 | 「逐帧提取」导入一段 10 分钟以上视频 | 不 OOM；退出后 `Android/data/.../files/frameTemp` 被清空；导出的是原始分辨率 PNG |
| 完成通知 | 下载完成时的前台通知 | 正常收尾（不常驻、不重复） |
| **文件被外部删掉** | 用文件管理器删掉某个已下载的视频 → 进「已完成下载」 | 该记录标出 **「文件已丢失」**；点它提示"文件已被删除或移动…"（**不能**再说成"只有附加内容"）；右侧删除按钮可清掉记录。**应用不会自动删记录**，这是有意的。轨迹里出现 `[文件探测] … 原因=形态=content 媒体库行=… 可打开=… 磁盘存在=… 未知异常=…`（⑥ 之后四个信号都落轨迹，误报/漏报全靠它取证） |

## E. 2026-10-02 A 组 / B 组新增功能的验证步骤（含 B 组收尾三项）

> 这一节是新功能的"逐条怎么点"。装包后按顺序跑一遍即可（每步都给了**期望**）。

| 功能 | 怎么点 | 期望 |
|---|---|---|
| **设置备份** | 设置 → 备份设置 | Toast「已导出：BDT-设置备份-<时间>.json」；`Download/BDT` 里出现该文件；内容是 JSON（`schema/exportedAt/appVersion` + 命名规则等） |
| **设置恢复** | 改一项设置（如命名规则）→ 设置 → 恢复设置 → 选刚才那个 JSON | Toast「已恢复设置（只覆盖备份里有的项）」；**只有备份里有的项被改回**，其它设置必须原样不动 |
| **诊断日志** | 存储管理 → 诊断日志 → 查看 | 对话框显示最近 ≤500 行轨迹；「导出」能在 `Download/BDT` 生成 `.txt`；「清空」后文件为空、界面变空 |
| **下载目录文件（孤儿）** | 存储管理 → 下载目录文件 | 列出 `Download/BDT`（含子目录）的文件与大小，并标「有记录 / 无记录（孤儿）」；用文件管理器丢一个文件进目录再刷新，应标为孤儿 |
| **失败项重试** | 造一个失败任务（或直接看现有失败项） | 「正在下载」顶部出现「有 N 个任务下载失败 → 全部重试」；点它任务重新开始 |
| **批量分享** | 下载管理 → 完成后右上进入编辑态 → 勾选多项 → 分享 | 系统分享面板出现；发给聊天 App 后**对方能打开视频**（验证 URI 读授权是否生效） |
| **批量移动** | 同上 → 移动到 → 填 `番剧` → 移动 | Toast「已移动 N 个文件到 番剧/」；文件管理器里文件进 `Download/BDT/番剧/`；**「已完成下载」里点开仍能正常打开**（记录 URI 不变） |
| **仅 Wi-Fi 下载** | 设置 → 打开「仅 Wi-Fi 下载」→ 关掉 Wi-Fi 用移动数据 → 解析一集点下载 | 应被拦下并提示「已开启『仅 Wi-Fi 下载』，当前不是 Wi-Fi，先不开始」（**注意不能断网太久**：AI 会话本身要用网络） |

| **通知动作** | 下载中点开通知 | 有「全部暂停」「全部取消」两个按钮；点「全部暂停」任务停住；点「全部取消」任务被取消（**已完成的记录不能被删掉**） |
| **全界面 i18n**（E1–E11b2 结项） | 系统语言切英文 → 依次看：下载管理（含卡片/对话框）、首页、工具、设置、存储管理、解析页、用户页、追番、版权申请、投诉、版本信息、风控提示、逐帧提取、线路配置、命名规则、设备信息、通知栏 | 这些界面的文案**全部英文**（数百条字符串已双套）；通知渠道名与两个按钮也是英文。**已知例外**（§16.9 遗留）：`NumberUtils` 的「万/亿」单位、线路名等**数据值**、以及少数 core 层错误兜底仍是中文 |
| **批量重命名**（B2 收尾，新） | 下载管理 → 完成后右上进入编辑态 → 勾选多项 → 重命名 → 填新基名（如 `我的视频`）→ 确认 | Toast 报出**回读到的真实文件名**（`已重命名 N 个文件：…`）；文件管理器里名字改了、**扩展名没变**；「已完成下载」里点开**仍能播放**（记录 URI 不变），**列表那一行的标题也变成新基名**（含撞名产生的 `(N)`）；轨迹出现 `批量重命名: 旧=… 期望=… 回读=… 更新行=… 判定=…`。**撞名时（目录里本来就有同名文件）Toast 里的名字会带 `(N)`** —— 这是 ROM 行为，不是 bug |
| **点通知直达**（B3 收尾，新） | 下载中下拉通知栏 → 点「缓存通知」 | **直接落在「下载管理 → 正在下载」页**（以前只打开 App/上次停留的页面）。App 已在前台时点通知也要跳过去（`singleTask` → `onNewIntent`）；连点两次不应出现重复页面 |
| **纯模块文案本地化**（收尾，新） | 系统语言切英文 → 把某个已下载视频删掉 → 进「已完成下载」 | 标签显示英文 **`File missing`**（不再写死中文）；点那条记录，Toast 是英文 `The file was deleted or moved …`；纯附加内容的记录显示 `Extras only (no media file)` |
| **崩溃日志**（§16.1，**条件触发**） | 遇到一次真实崩溃后重开 App → 看崩溃页 → 存储管理 → 导出诊断日志（或 `adb-shell cat .../files/logs/crash.log`） | 崩溃页显示「发生错误：…」+ 一行「完整堆栈已写入…crash.log」提示；`logs/crash.log` 里是**完整堆栈**（含时间/线程/进程）；导出的 `BDT-诊断日志-*.txt` 开头有「===== 崩溃日志（crash.log）=====」段。**没有真实崩溃就验不到这条**（不人为造假崩溃） |

**已知行为（别当成 bug）**：
- **重命名会同时改记录标题**（§16.2）：列表那一行显示的名字 = **回读到的真实文件名去掉扩展名**
  （撞名时会带 `(N)`），与文件管理器里所见一致；`savePath` 是 content URI（`_ID` 不变）所以记录照旧有效。
- 通知里的「全部暂停 / 全部取消」是**聚合语义**（只能做"全部"），**没有单任务按钮**，这是有意的。

## 附：这台机器上 MediaStore 的四个怪癖

看到下面这些症状，基本可以直接怀疑是它们（**都已在 v3.3.0 里绕开**）：

1. **写入撞名 → 自动改名**：往 `Download/` 写已存在的名字，MediaStore 会改成 `xxx (1).mp4`、`(2)`，**不报错**。
2. **事后改名也在 `(N)` 上加**：`update(DISPLAY_NAME)` 想改回正式名，会继续加后缀；而且
   **`_data` / 回读出来的名字可能与磁盘上的真实名字不一致**。
3. **app 动不了别人（媒体库）的文件**：`File.delete()/renameTo()` 会 EACCES；`File.isFile` 恒 false；
   **连 `File(dir).listFiles()` 都可能返回 null** → 所以代码里一律改成"问 MediaStore"（`RELATIVE_PATH` 前缀 →
   `_data` 前缀）+ `scanFile` 探测/扫目录兜底。
4. **MIUI 过滤 app 的 logcat**：同一段代码有时一条日志都没有 → 关键步骤一律**落文件**（见第 0 节的轨迹文件）。

另外两条实证结论：

- **任何"在成品已落盘之后再删东西"的设计都不安全**：曾经因为"回读名字 ≠ 磁盘真实名字"，
  目录直删把**刚交付的新文件**删掉过。现在的顺序是 **交付前挪开 → 写入 → 成功后删除**，
  删除只允许发生在"成品还不存在时"或"严格按 `_ID` 排除自己"。
- **删"不是本 app 拥有"的媒体行必须走 `MediaStore.createDeleteRequest`**（Android 11+），
  直接 `resolver.delete` 会被拒（表现为静默 `实际删除=0`）。
