# 真机验证清单（每次发版后照着跑）

> 这份清单是 2026-10-01 那轮真机调试的产物：当时的每个坑都对应下面的一条检查。
> **不必全跑**，但 **A / B / C 三组是必跑**（它们覆盖"用户升级会打不开""下完的文件丢了/多份"这两类最痛的后果）。

机型参考：小米 `2510DRK44C`（Android 16 / SDK 36）。其它机型同样适用，但要注意
[文末的四个 ROM 怪癖](#附这台机器上-mediaStore-的四个怪癖)只在这台机器上被完整复现过。

---

## 0. 准备

1. 覆盖安装新包（同一把签名，**登录状态与设置都不会丢**）：
   ```bash
   adb install -r app-alpha-arm64-v8a-release.apk
   # 或在手机上点 APK 安装
   ```
2. 确认版本与显示名：
   ```bash
   adb shell dumpsys package com.whyd9527.bilibilias | grep -E "versionName|versionCode|lastUpdateTime"
   ```
   - 期望：`versionName` 与 Release 一致；应用名在桌面显示为 **BDT**。
3. 轨迹文件位置（**排查任何"删除/清理没生效"先看它**）：
   ```
   /sdcard/Android/data/com.whyd9527.bilibilias/files/logs/download-trace.log
   ```
   ```bash
   adb shell cat /sdcard/Android/data/com.whyd9527.bilibilias/files/logs/download-trace.log | tail -20
   ```
   > MIUI 会过滤 app 自己的 logcat，所以这个文件是**唯一可靠**的取证渠道。

| 步骤 | 期望 |

## B. 下载与交付（必跑）

| 步骤 | 期望 | 怎么看 |
|---|---|---|
| 1. 解析一集并下载 | 完成后下载目录里**只有 1 份**、名字**恰好是正式名**、没有 `.part` | 文件管理器看目录 |
| 2. **换一个音频质量后重下同一集** | 仍然**只有 1 份**、名字仍是正式名、**没有 `xxx (1).mp4`**；新文件的大小/时间戳与旧的不同（证明是新下的那份） | 目录 + 轨迹 |
| 3. 看轨迹 | 出现 `交付前挪开同名旧文件: … 枚举=N 目标=N 成功=N` 与 `交付成功，清理挪开的旧文件: 目标=N 实际删除=N` | `download-trace.log` |
| 4. 产物是否完好 | 能播放、有声音、时长与视频一致 | 播放器；或按下方脚本抽查 MP4 结构 |

**抽查 MP4 结构**（在手机上用 MT 管理器或 Python 都能跑）：

```python
import struct, os
p = "下载目录/xxx.mp4"; f = open(p, "rb"); size = os.path.getsize(p)
def walk(f, s, e, d=0, out=None):
    pos = s
    while pos + 8 <= e:
        f.seek(pos); h = f.read(8)
        if len(h) < 8: break
        sz, typ = struct.unpack(">I4s", h); hsz = 8
        if sz == 1: sz = struct.unpack(">Q", f.read(8))[0]; hsz = 16
        elif sz == 0: sz = e - pos
        if sz < hsz: break
        out.append((d, typ.decode("latin1"), pos, sz))
        if typ in (b"moov", b"trak", b"mdia", b"minf", b"stbl"): walk(f, pos + hsz, pos + sz, d + 1, out)
        pos += sz
top = []; walk(f, 0, size, 0, top)
print("顶层:", [t[1] for t in top if t[0] == 0])          # 期望 ftyp/free/mdat/moov
hdls = []
for d, t, pos, sz in top:
    if t == "hdlr": f.seek(pos + 16); hdls.append(f.read(4).decode("latin1"))
print("轨道:", hdls)                                       # 期望含 vide 与 soun
```

## C. 重复文件检查 / 清理（必跑）

1. 先造一份"重复"：用文件管理器把某集**复制**一份，改名成 `原名 (1).mp4`。
2. 打开 app → **下载管理**：
   - 期望顶部出现 **「发现 N 组重复下载文件 … 去清理」**；
   - 若只有「检查重复下载文件」：点一下（首次会要 `READ_MEDIA_VIDEO` 权限，**必须允许**，否则看不到"不是本 app 拥有"的副本）。
3. 点「去清理」→ 期望列出 `保留：<正式名>` + 副本默认勾选 →「删除选中 (N)」。
4. 点删除：
   - 若副本是**本 app 下载的** → 直接删掉；
   - 若是**别的 App / 上一版安装留下的** → 会弹**系统确认框**（「要允许 BDT 删除这个视频吗？」）→ 允许后才删。
5. 期望结果：目录回到 1 份；卡片消失；轨迹里 `清理重复文件: … 实际删除=n 待用户确认=m`。

> 这一步删除失败（`实际删除=0` 且没有系统弹窗）＝回归，先看轨迹再动手。

## D. 其它回归点（每隔几次发版跑一次）

| 项 | 步骤 | 期望 |
|---|---|---|
| 失败不再静默 | 用系统分享发一段**非 B 站文本**（如 `abc`）给 BDT | 出现 `Error：没有识别出 B 站链接或 ID` 卡片 +「点击重试」，点重试会重新解析 |
| 分享入口 | 从 B 站 App 分享一条视频链接到 BDT | 链接自动进输入框并解析成功 |
| 剪贴板门槛 | 未同意隐私政策时启动 | **不读剪贴板、不请求 GitHub**（可用 GitHub 限流计数或抓包核对） |
| 取消/暂停 | 下载中途暂停再继续、取消 | 不应被记成「下载失败」；恢复后能接着下 |
| 抽帧工具 | 「逐帧提取」导入一段 10 分钟以上视频 | 不 OOM；退出后 `Android/data/.../files/frameTemp` 被清空；导出的是原始分辨率 PNG |
| 完成通知 | 下载完成时的前台通知 | 正常收尾（不常驻、不重复） |

## 附：这台机器上 MediaStore 的四个怪癖

看到下面这些症状，基本可以直接怀疑是它们（**都已在 v3.3.0 里绕开**）：

1. **写入撞名 → 自动改名**：往 `Download/` 写已存在的名字，MediaStore 会改成 `xxx (1).mp4`、`(2)`，**不报错**。
2. **事后改名也在 `(N)` 上加**：`update(DISPLAY_NAME)` 想改回正式名，会继续加后缀；而且
   **`_data` / 回读出来的名字可能与磁盘上的真实名字不一致**。
3. **app 动不了别人（媒体库）的文件**：`File.delete()/renameTo()` 会 EACCES；`File.isFile` 恒 false；
   **连 `File(dir).listFiles()` 都可能返回 null** → 所以代码里一律改成"问 MediaStore"（`RELATIVE_PATH` 前缀 →
   `_data` 前缀）+ `scanFile` 探测/扫目录兜底。
4. **MIUI 过滤 app 的 logcat**：同一段代码有时一条日志都没有 → 关键步骤一律**落文件**（见第 0 节的轨迹文件）。

另外两条实证结论：

- **任何"在成品已落盘之后再删东西"的设计都不安全**：曾经因为"回读名字 ≠ 磁盘真实名字"，
  目录直删把**刚交付的新文件**删掉过。现在的顺序是 **交付前挪开 → 写入 → 成功后删除**，
  删除只允许发生在"成品还不存在时"或"严格按 `_ID` 排除自己"。
- **删"不是本 app 拥有"的媒体行必须走 `MediaStore.createDeleteRequest`**（Android 11+），
  直接 `resolver.delete` 会被拒（表现为静默 `实际删除=0`）。
